# 04 — Security: module-owned authorization policies

**What to build:** Every CMS admin resource enforces per-resource `view/create/update/delete` authorization through the Phase 1 `AccessControlInterface` / `PermissionGroup` contract — closing OWASP A01 Finding 1.2. Today only the Module-management page checks a permission; every other resource is open to any panel user.

**Blocked by:** 03 (portability) — lands last in the foundation-first order, on green dual-DB CI.

**Status:** DONE (branch `feature/cms-module-policies`, not pushed)

- [x] Each module **declares** `view/create/update/delete` permissions via `PermissionRegistrarInterface` / `PermissionGroup`. Added groups: pages, posts, media (view/update/delete), content-types, content-entries, menus (shared by MenuResource + MenuItemResource), forms, form-submissions (view/delete), notification-logs (view/delete). Each declared in the module's `bootModule()`/`registerModule()` guarded by `bound(PermissionRegistrarInterface)` (headless-safe), mirroring cms-api's `api-tokens.manage`. No host `App\` coupling — arch test green. **Chose the trait-over-policy approach:** a shared `AuthorizesWithPermissions` concern in cms-core (not a Laravel policy per model) because Filament resources authorize through static `can*` methods, and every module already depends on cms-core.
- [x] Filament resources authorize through those permissions. `AuthorizesWithPermissions` maps `canViewAny/canView/canCreate/canEdit/canDelete/canDeleteAny` → `<key>.<ability>` via `AccessControlInterface`; **fails safe** (denies) when the contract is unbound. Applied to all 10 module resources; ApiTokenResource keeps its existing `api-tokens.manage` gate. (Category/Tag = legacy host Collection taxonomy, out of the module scope; post taxonomy is edited inside PostResource. Audit-log resource ships gated in ticket 05.)
- [x] Shield remains the assignment UI only (no per-resource policy generation; no `define_via_gate` bypass — explicit permissions, matching the existing convention).
- [x] Baseline role set — `CmsBaselineRolesSeeder` (super_admin/admin = all, editor = content CRUD minus mgmt scopes, author = content create/update on pages/posts/content-entries/forms/media, viewer = view-only), materialised from the registrar (never hand-listed). Wired into `CoreSetupSeeder` so the demo admin's `super_admin` role is granted the CMS permissions (otherwise gating would lock the owner out). **Default self-registered role = `super_admin` (assigned on personal-team creation); formal self-registration role model is ticket 07 / OWASP A04.**
- [x] Behaviour guarantees: `CmsResourceAuthorizationTest` (dataset over all 10 resources) proves a no-permission user is forbidden every action and a view-only user can view but not delete; the existing per-resource Livewire tests now grant explicit permissions and still exercise the happy path.
- [x] DoD: no ungated CMS resource; per-resource forbidden tests pass; arch test green; Pint + PHPStan max clean; full suite **534 green on SQLite** (MySQL + Postgres verified by ticket 03's CI matrix on push — no pgsql/mysql PDO locally). **Follow-up noted:** the ThemeManagement / WidgetOverview admin *pages* (not resources) are still open; gate in a later pass.
